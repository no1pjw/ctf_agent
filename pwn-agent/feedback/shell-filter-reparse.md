# Shell filter reparsing

## 원문 필터 뒤의 셸 확장 단계도 따로 모델링한다

- **증상:** 입력 원문에서 공백과 명령 이름, 메타문자를 substring으로 거부하지만, 통과한 문자열을 인용 없이 셸 명령에 이어 붙인다.
- **재사용 가능한 교훈:** 필터가 보는 문자열과 셸이 확장 후 실행하는 토큰은 다를 수 있다. parameter expansion으로 공백 역할을 만들거나, 허용된 escape 표현을 실행 시점에 디코딩하고, command substitution 안에서 새 셸의 명령 문자열을 구성하는 식의 다단계 재해석을 확인한다. 각 parse 단계가 backslash나 따옴표를 한 겹씩 소비한다는 점을 단계별로 추적한다.
- **가장 싼 확인법:** 위험 없는 표식 문자열로 최소 payload를 만들고, (1) 원문이 blacklist를 통과하는지 코드로 검사한 뒤 (2) 동일한 `/bin/sh`에서 확장 결과의 인자 경계와 출력만 관찰한다. 금지 명령 자체를 먼저 시도할 필요는 없다.
- **환경/적용 한계:** `${IFS}`의 값과 splitting, `echo`의 backslash·octal 처리, `$0 -c` 동작은 셸 구현과 호출 방식에 따라 달라진다. `printf` 사용 가능 여부를 먼저 보고, 불가능하면 대상과 같은 셸에서 escape 동작을 별도 검증한다. 명령 전체가 강하게 인용되거나 셸을 거치지 않는 실행 API라면 적용되지 않는다.

## Command substitution에서는 출력 채널을 분리해 본다

- **증상:** command substitution 내부의 표준 출력은 바깥 명령의 인자로 흡수되거나 후속 오류에 묻혀, 실행 성공 여부가 보이지 않는다.
- **재사용 가능한 교훈:** 셸 치환이 포획하는 것은 보통 `stdout`이므로, 이미 허용된 관찰 채널인 `stderr`는 독립적인 실행 표식이나 결과 확인 경로가 될 수 있다.
- **가장 싼 확인법:** 민감하지 않은 고정 표식을 각각 `stdout`과 `stderr`로 보내 transcript에서 어느 채널이 보존되는지 비교한다.
- **환경/적용 한계:** 서비스 wrapper, 원격 프로토콜, 웹 서버가 두 스트림을 합치지 않거나 `stderr`를 버릴 수 있다. 데이터 유출 수단으로 가정하기 전에 고정 표식으로 확인하고, 실제 프로그램 오류와 구분한다.

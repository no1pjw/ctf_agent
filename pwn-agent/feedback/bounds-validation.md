# Bounds validation lessons

## 스케일된 signed index의 modular alias

- **증상:** 배열 접근이 상한만 검사하고 음수 인덱스를 허용하며, 주소를 `base + stride * index` 형태의 고정 폭 정수 연산으로 만든다.
- **재사용 가능한 교훈:** 단순한 작은 음수뿐 아니라 `stride * index`가 정수 폭에서 wrap되어 정상 슬롯이나 그 인접 영역과 같은 변위를 만드는 큰 음수도 후보가 된다. 따라서 디컴파일러의 배열 표기만 보고 접근 가능 범위를 판단하지 않는다.
- **가장 싼 확인법:** 인덱스의 파싱 폭·signedness, 실제 곱셈 폭, stride를 확인한 뒤 모듈러 식 `stride * index mod 2^word_size`만 계산해 목표 슬롯과의 별칭을 정적으로 검사한다.
- **환경/적용 한계:** 컴파일된 기계어가 wrap되는 고정 폭 연산을 실제로 사용해야 한다. 컴파일러가 overflow 불가능성을 가정해 최적화했거나 checked arithmetic, 하한 검사, 더 넓은 중간값을 쓰면 같은 결론을 적용할 수 없다.

## 거부 전에 발생하는 입력 부작용

- **증상:** 프로그램이 `scanf` 같은 입력 함수로 값을 목적지에 먼저 저장한 뒤 범위를 검사하고, 실패 시 오류만 출력하고 계속 실행한다.
- **재사용 가능한 교훈:** 해당 작업이 최종적으로 거부돼도 목적지 쓰기는 이미 발생했다. 목적지가 다른 객체와 alias되거나 OOB 주소 계산으로 선택될 수 있다면, 실패 경로 자체가 제한된 값 쓰기 primitive가 된다.
- **가장 싼 확인법:** 소스나 짧은 disassembly에서 `parse/store -> compare -> reject` 순서를 확인하고, 거부 경로가 저장값을 복원하거나 프로세스를 종료하는지도 함께 본다. 가장 가까운 비중요 필드의 변경 여부를 음성 대조군으로 확인한다.
- **환경/적용 한계:** 파서가 변환에 성공해야 하며 목적지 타입과 표현 범위를 지켜야 한다. 거부 경로가 즉시 비복귀 종료하거나 값을 복원하고, 변경된 객체가 그 전에 소비되지 않으면 exploit primitive가 되지 않는다.

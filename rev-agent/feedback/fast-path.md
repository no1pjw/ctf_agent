# Reverse fast-path lessons

## Launcher 경로를 다시 찾지 않기

- 증상: 분석 전에 스킬 파일을 다시 열거나 intake·input·work 위치를 검색하면서 여러 도구 턴을 소비한다.
- 재사용 가능한 교훈: launcher가 제공한 환경 변수와 프롬프트의 정확한 경로를 권위 있는 값으로 사용한다. 이미 주입된 스킬은 다시 읽지 않는다.
- 가장 싼 확인법: `$CTF_REV_INPUT_DIR`, `$CTF_REV_WORK_DIR`와 지정된 intake 파일의 존재만 한 번 확인한다. 경로가 유효하면 `rg --files` 같은 전역 탐색을 하지 않는다.
- 환경/적용 한계: launcher 밖에서 직접 시작한 세션처럼 경로가 제공되지 않은 경우에만 한 번의 제한된 위치 확인을 허용한다.

## 도구 호출 수보다 출력량을 제한하기

- 증상: 도구 호출 횟수는 적은데도 큰 `readelf`, `objdump`, `xxd` 결과 뒤에서 추론 시간이 급증한다.
- 재사용 가능한 교훈: 호출을 무조건 합치는 것보다 모델에 전달되는 출력의 크기와 관련성을 제한하는 것이 중요하다. 최초 probe는 16 KiB 이하로 유지하고, 전체 심볼·섹션·raw blob을 한꺼번에 출력하지 않는다.
- 가장 싼 확인법: 먼저 파일 형식, 결정적 심볼·문자열, entry 또는 `main`의 좁은 slice만 본다. 다음 출력은 앞 단계에서 참조된 주소나 file offset 주변으로 제한한다.
- 환경/적용 한계: packer, VM dispatcher 또는 self-modifying code 때문에 전체 구조가 실제로 필요한 경우에도 먼저 직접 flag 경로가 없다는 증거를 확보한 뒤 범위를 넓힌다.

## 큰 blob은 참조 offset부터 보기

- 증상: opcode, chain, resource 같은 데이터 파일 전체를 disassemble 또는 hexdump하고 관련 없는 내용을 오래 해석한다.
- 재사용 가능한 교훈: loader나 validator가 사용하는 base address, index, table pointer를 먼저 복구하고 그 주변의 bounded window만 검사한다.
- 가장 싼 확인법: 코드에서 파일 매핑 주소와 참조 offset을 찾은 뒤 `xxd -s/-l`, `dd`, address-limited `objdump` 중 하나로 필요한 구간만 본다.
- 환경/적용 한계: 참조가 동적으로 계산되어 정적 offset을 구할 수 없을 때만 작은 추적기나 격리 실행으로 실제 접근 구간을 확인한다.

## 검증 payload와 제출 wrapper를 구분하기

- 증상: 역산한 바이트가 프로그램의 수학적 검사를 통과하지만 기록된 `PREFIX{...}` 형식과 다르다는 이유로 올바른 복원식을 실패로 판정한다.
- 재사용 가능한 교훈: 프로그램이 직접 받는 payload와 scoreboard에 제출하는 flag 문자열은 다를 수 있다. 형식 접두사·중괄호는 외부 wrapper일 가능성을 먼저 확인한다.
- 가장 싼 확인법: 역산 payload의 모든 내부 제약을 독립 검증한 뒤, 기록된 형식이 있으면 `PREFIX{payload}`를 구성해 형식만 별도로 확인한다. wrapper 불일치만으로 산술 가설을 폐기하지 않는다.
- 환경/적용 한계: 프로그램 자체가 접두사와 중괄호까지 비교한다는 증거가 있으면 wrapper를 별도로 추가하지 않는다.

## 플래그 측정은 명시적 출력만 인정하기

- 증상: traceback, assertion, 소스 코드 또는 설명에 포함된 `PREFIX{...}` 문자열이 실제 획득 시각보다 먼저 플래그 후보로 집계된다.
- 재사용 가능한 교훈: 자동 측정에서는 일반 문자열 검색 대신 성공 계약인 독립된 `FLAG=<value>` 출력만 플래그로 인정한다.
- 가장 싼 확인법: command output 또는 최종 응답의 완전한 한 줄이 `FLAG=<형식에 맞는 값>`인지 확인한다.
- 환경/적용 한계: 이는 벤치마크 계측 규칙이다. 사람이 분석하는 후보 문자열 자체를 버리라는 의미는 아니다.
